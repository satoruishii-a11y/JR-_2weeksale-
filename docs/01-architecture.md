## ① 作る — Creative Generator の内部

```

（素材・コピー・ブランド）  （カット割り・軸・タイポグラフィ）
      │                      │
      └──────────┬───────────┘
                 ▼
        ┌─────────────────┐
        │ variants.ts     │  軸の直交配列展開 → N パターン
        └────────┬────────┘   各パターンに 6桁ハッシュを採番
                 ▼
        ┌─────────────────┐
        │ resolve.ts      │  ${axis.x} / ${copy.y} / $switch / $ref を解決
        └────────┬────────┘   （パターン × アスペクト比）ごとに1つの設計図
                 ▼
        ┌─────────────────┐
        │ timeline.ts     │  xfade の重なりを引いて実尺を確定
        │ draw.ts         │  テロップを透過PNGに焼く（禁則処理・自動縮小）

        │ ffmpeg.ts       │  Ken Burns / トランジション / 合成 / BGM
        └────────┬────────┘

        ┌─────────────────┐
        │ manifest.ts     │  決定タグ + 再現用の設計図を JSON / CSV に
        └─────────────────┘
```

### 設計上の決めごと

**純粋関数として組む。**
`(テンプレート, プロジェクト, 軸の値, アスペクト比)` から出力が一意に決まります。
乱数を使わないので、同じ入力からは常に同じ動画が出ます。
「先月の当たりクリエイティブの色だけ変えたい」が確実に再現できるのは、この性質のおかげです。

**テロップは ffmpeg の drawtext を使わない。**
日本語の折り返し・禁則処理・字間・帯・縁取りを自前で制御するため、
`@napi-rs/canvas` で透過PNGに焼いてから合成しています。
drawtext を持たない ffmpeg ビルドでも動く、という副次的な利点もあります。

**アスペクト比は「同じ設計を解決し直す」。**
9x16 用に作った動画をトリミングするのではなく、
`$switch on: orientation` で位置とサイズを解決し直して、縦横それぞれに最適な組版で描画します。

**セーフエリアは配信面ごとにプロファイルを持つ。**
インストリームとShortsでは塞がれる領域が違うので、同じ基準で見ると警告が実態と合いません。
`--safe-area instream|shorts` で切り替えます。

## ② 配信する — 手動入稿にした理由

Google Ads API での自動入稿は技術的には可能ですが、月30本規模では見送りが妥当です。

- **投資対効果**: 入稿作業は1本あたり数分。月30本で1〜2時間。
  自動化には本番トークン申請と数週間の開発が要り、回収に時間がかかります。
- **リスク**: 誤配信の金銭的影響が直接発生します。
- **実務**: 入札戦略・除外設定・オーディエンスは結局人が判断する部分が残ります。

一方で **実績取得は完全に自動化する価値があります**。日次で全クリエイティブを引くのは
手作業では現実的でなく、かつ機械的な処理なので事故りません。

自動化するのは以下だけです。

| 取得元 | 取るもの | 頻度 |
|---|---|---|
| Google Ads API | 表示回数、視聴回数、視聴率、平均視聴時間、CPV、CTR、CV、費用 | 日次 |
| YouTube Analytics API | 秒単位の視聴維持率カーブ、平均再生率 | 日次 |

**人がやるのは1つだけ** — 入稿時に動画タイトルとアセット名へ `creative_id` を入れること。
これで実績と決定タグが自動で突き合わさります（`docs/02-creative-id.md`）。

## ③ 分析する — 2種類のタグを1つのキーで束ねる

```
creative_id  ─┬─ 決定タグ    生成時に確定（manifest.json）
              ├─ 知覚タグ    LLMが完成動画から付与（1回だけ）
              └─ 実績        日次で更新
```

キーが1つに揃っているので、結合はただの JOIN です。
「どの動画のレポートか分からなくなる」という、この種の運用で最も起きやすい事故が
構造的に起きません。

## ④ ダッシュボード — 自由度と自動更新を両立させる構成

環境は後決めという前提なので、**データ層とUI層を分けて、どちらも差し替え可能にします**。

```
Warehouse（Postgres か BigQuery）
   ▲                    ▲
   │ 日次ジョブが書く      │ UI が読む
Ingestor              Dashboard（Next.js）
```

- Warehouse を独立させておけば、UIをLooker Studioに寄せることも、
  逆にBIをやめて自前UIに寄せることも後から選べます。
- 「動画プレビュー」「タグ別スコア」「LLMの示唆コメント」を同じ画面に出すには
  BIツールでは表現力が足りないので、UIは Next.js を推奨します。
- クライアント別のログインと権限分離もUI層の要件です。

詳細は `docs/05-dashboard.md`。
